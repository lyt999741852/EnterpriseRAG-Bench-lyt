# RAG 联调控制台：开发设计文档

**状态：设计已确认，待模块实施**  
**隔离边界：`rag-debug-console/` 是独立应用根目录；不得修改或运行现有 RAG 的 `src/`、`configs/`、`outputs/`、`corpus/`、`.index_cache/`、`.pageindex_cache/`。**

## 1. 目标与非目标

本项目提供一个用于可视化联调的 Web 控制台：用户能在对话式界面中手动提问或从 500 题题库中选择题目，查看检索结果、最终答案和评测指标；还能将固定的 50 题或全部 500 题提交为后台测试任务。

本项目不是对当前 RAG 算法、索引、配置或评测逻辑的改造。现有仓库仍可独立测试优化，控制台不与该工作并行写入或争用同一运行资源。

## 2. 已知系统约束

- 现有主链路为 Elasticsearch Hybrid → remote reranker → PageIndex → evidence selection → LLM generation。
- 现有流水线产出 `answers.jsonl`、`route_trace.jsonl`、简单指标及可选官方评测 `results.json`。
- 题库 `questions.jsonl` 含评测 gold 字段，且已被 `.gitignore` 忽略；推理路径必须保持 question-only。
- 现有配置默认直接使用内网 LLM、reranker、ES 与 PageIndex；其中 50/500 评测尤其会占用共享资源。

## 3. 目录与进程隔离设计

### 3.1 新应用边界

所有新代码仅新增在以下目录中：

```text
rag-debug-console/
├── docs/
│   └── DEVELOPMENT_DESIGN.md
├── backend/                 # 新 API 与任务服务
├── frontend/                # 新 Web 前端
├── data/                    # 仅题库的受控只读副本/索引
├── runtime/                 # 新应用的 SQLite、日志、任务目录（gitignore）
├── scripts/                 # 启动、导入、健康检查脚本
└── README.md
```

控制台不得在项目根目录创建 `outputs/`、缓存或临时文件，不得复用现有 `pipeline.name`，不得写入现有 RAG 目录。

### 3.1.1 开发文件清单

第一阶段仅在 `rag-debug-console/` 中新增下列文件；每个模块的实现、验证和提交会记录在 `TODO.md`。

```text
rag-debug-console/
├── README.md                         # 独立启动、架构、版本与运行手册
├── TODO.md                           # 模块状态、验收、提交 SHA 与运行记录
├── .gitignore                        # runtime、环境变量、前端构建产物
├── docs/
│   └── DEVELOPMENT_DESIGN.md         # 本设计与接口契约
├── backend/
│   ├── app/                          # API、领域模型、服务、适配器与 worker
│   └── tests/                        # 后端单元/API 契约测试
├── frontend/
│   ├── src/                          # 对话、题库、批量任务、历史运行页面
│   └── tests/                        # 前端组件与端到端测试
└── scripts/                          # 独立启动、检查和导入脚本
```

实现时禁止使用相对路径跨出 `rag-debug-console/` 来读取或写入当前 RAG 工作目录；允许的跨边界调用只有受版本控制的 HTTP 调试 API。

### 3.2 与现有 RAG 的连接方式

推荐在后续实施前，由现有 RAG 提供一个稳定、只读的**调试服务接口**；控制台通过 HTTP 调用它，不导入或修改当前 `src/`。接口在一个独立的服务进程中运行，负责创建 RAG 执行上下文并返回调试轨迹。

在该接口未准备好时，控制台可以先完成前端、题库浏览、运行记录及 API mock；不得通过直接调用 `python -m src.pipeline` 的方式接入生产页面。

### 3.2.1 两种运行模式

| 模式 | 用途 | RAG 版本选择 | 默认场景 | 结果可复现性 |
|---|---|---|---|---|
| `pinned`（固定版本） | 稳定回归与正式比较 | 明确指定已发布的服务版本、配置指纹与索引版本 | 日常 50 题、全量 500 题 | 强：历史结果永不随新优化改变 |
| `live`（当前联调） | 验证最新已发布优化 | 用户选择“最新已发布”调试服务版本 | 手动单题联调 | 每条记录仍保存实际版本指纹 |

`live` 不读取开发中的代码、临时缓存或未完成索引；它只跟随**已发布且健康检查通过**的 RAG 调试服务。优化完成后由 RAG 侧发布新服务版本，控制台才可选择并调用该版本。控制台不会自动替换既有会话或批量运行的 RAG 版本。

### 3.3 资源互斥

批量任务必须申请共享资源锁 `rag-evaluation`：锁存在时仅能排队或拒绝启动。单题联调默认低并发（1），也需申请 `rag-inference` 锁；管理员可在服务端暂停控制台。锁状态由独立调度服务维护，而不是由前端判断。

## 4. 用户功能与验收

| 功能 | 行为 | 验收条件 |
|---|---|---|
| 对话历史 | 上部顺序显示输入、回答、文档引用和耗时 | 刷新/切换运行后可恢复同一会话记录 |
| 输入框 | 支持任意手动问题、发送、取消和清空 | 一次请求只创建一条可追踪的单题运行 |
| 500 题侧栏 | 一级按题目分类，二级按题号显示并可搜索 | 点击题号会填入输入框，用户可再编辑后发送 |
| 单题调试 | 展示路由、各检索视图、RRF、rerank、PageIndex、证据、生成结果 | 每个字段标明是否真实数据、耗时和异常 |
| 日常 50 题 | 通过固定清单创建后台批量任务 | 每次执行使用相同、带版本号的题目清单 |
| 全量 500 题 | 后台全量运行，显示队列、进度、取消/失败状态 | 不阻塞浏览或单题历史；锁冲突时不启动 |
| 评测指标 | 展示单题与聚合指标、可钻取失败题 | 区分即时检索指标与官方 Judge 指标 |
| 运行历史 | 保存配置快照、题目集版本、产物链接与日志 | 任意结果可以定位至不可变运行 ID |

## 5. 前端页面设计

### 5.1 统一布局

- 顶栏：服务状态（ES、Reranker、LLM）、当前环境、资源锁状态。
- 左栏：工作区切换、500 题分类树、固定 50 题和全量 500 题入口。
- 主区：默认单题联调；批量任务和历史运行在同一壳中切换。

### 5.2 单题联调页

1. 对话区显示问题、回答、引用父文档 ID、耗时、错误状态。
2. 执行轨迹为可折叠五段：路由、检索、重排、PageIndex、证据/生成。
3. 检索段保留每路 query、候选数、分数、合并结果；证据段保留实际进入上下文的 chunks 与文档。
4. 对 benchmark 题目，可在独立“评测”折叠区展示文档 Recall、无效额外文档数；官方 Judge 返回后再展示 Correctness、Completeness 与理由。

### 5.3 批量测试与历史页

- 批量页：任务状态、排队原因、完成进度、预计剩余时间、总体指标、题目表格和失败项筛选。
- 历史页：运行 ID、发起时间、题集版本、RAG 配置指纹、状态和结果摘要。点击单题回到与单题联调一致的轨迹视图。

## 6. 后端 API 与数据契约

### 6.1 API（第一版）

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/questions` | 获取分类树、搜索和题目摘要；不返回 gold 字段 |
| `GET` | `/api/questions/{id}` | 题目详情与类别；不返回 gold 字段 |
| `POST` | `/api/chat-runs` | 创建单题联调请求 |
| `GET` | `/api/chat-runs/{id}` | 获取回答、执行轨迹、即时指标 |
| `POST` | `/api/batch-runs` | 创建 `daily-50` 或 `full-500` 后台任务 |
| `GET` | `/api/batch-runs/{id}` | 获取状态、进度、聚合指标和日志摘要 |
| `POST` | `/api/batch-runs/{id}/cancel` | 请求取消尚未完成的任务 |
| `GET` | `/api/runs` | 查询运行历史 |
| `GET` | `/api/health` | 控制台、调试服务与资源锁状态 |

### 6.2 单题响应最小结构

```json
{
  "run_id": "chat_20260826_001",
  "question": {"id": "qst_0031", "text": "...", "origin": "catalog"},
  "status": "completed",
  "answer": {"text": "...", "document_ids": ["DOC-1827"]},
  "trace": {"route": {}, "retrieval": {}, "rerank": {}, "pageindex": {}, "evidence": {}, "generation": {}},
  "metrics": {"document_recall_pct": 100.0, "invalid_extra_docs": 0, "judge": null},
  "timing_ms": {"total": 8400}
}
```

### 6.3 数据安全规则

- `/api/questions` 和 `/api/chat-runs` 的服务模型只含 `question_id`、题目文本、分类、来源、显示名称；禁止携带 `gold_answer`、`answer_facts`、`expected_doc_ids`。
- 指标 worker 可在隔离的离线评测上下文读取 gold 字段，但不得将其写入聊天、检索或 prompt 日志。
- 前端不接触 LLM、reranker、ES 或评测 API 的密钥；所有密钥仅保存在后端环境变量中。

## 7. 批量任务与评测策略

1. 将 50 题清单写为版本化的只读数据文件，例如 `data/test-suites/daily-50.v1.json`；清单由当前项目负责人确认后固定。
2. 每次运行创建独立目录：`runtime/runs/<run_id>/`，其中包含输入清单副本、RAG 配置指纹、事件日志、回答、轨迹、指标及错误清单。
3. batch worker 仅从调试服务获得 question-only 执行结果；评测 worker 在任务完成后单独计算简单指标和可选官方 Judge 指标。
4. 任务状态为 `queued → running → evaluating → completed | failed | cancelled`；各状态及停止原因应写入事件日志。
5. 500 题任务默认串行，或由服务端受控提升并发；不得由浏览器传入并发参数。

## 8. 建议实施顺序（确认后执行）

1. **M0 基座与追溯：** 创建独立应用脚手架、环境文件、运行目录、资源锁接口及 `TODO.md`。
2. **M1 接口契约：** 定义并对接只读调试 API，同时用 mock 契约让前端先行开发；实现 `pinned` 和 `live` 的版本选择与记录。
3. **M2 题库与单题联调：** 实现题库导入、分类映射、固定 50 题清单、侧栏、聊天与可折叠执行轨迹。
4. **M3 批量与历史：** 实现后台队列、进度推送、取消、运行历史、配置快照及资源锁。
5. **M4 评测：** 接入评测 worker、指标钻取、异常处理和访问控制。
6. **M5 联调验收：** 只在当前 RAG 优化任务闲置且资源锁允许时完成端到端验证。

每个模块须遵循：`TODO → IN PROGRESS → DONE`；只有在代码检查、测试和设计验收均通过后才可标记 DONE。每次完成模块至少形成一个单用途 Git 提交；`TODO.md` 回填提交 SHA、测试命令及关键运行 ID。推送前执行本模块测试，推送后记录远端分支与 PR 链接（若创建）。
